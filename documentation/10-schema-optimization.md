# Schema-Optimierung (Migration 20260428165213)

## Überblick

Diese Migration behebt strukturelle Probleme im DB-Schema: unnötige Tabellen-Aufteilung, falsche Primary Keys, fehlende Zeitzonen, inkorrekte Datentypen und fehlende Sicherheits-Policies.

## Änderungen im Detail

### 1. `participation`-Tabelle aufgelöst

**Vorher:** Zwei Tabellen mit 1:1-Beziehung:
- `event_participation` (person_id, event_id, role)
- `participation` (event_participation_id FK, status, task_description)

**Nachher:** Alles auf `event_participation`:
- `status` (invitation_status_enum, DEFAULT 'Pending') direkt auf `event_participation`
- `task_description` wurde entfernt (war nirgends im Code verwendet)
- `participation`-Tabelle gelöscht

**Warum:** Jede Query brauchte einen unnötigen JOIN. Jeder Insert brauchte zwei Operationen. Die 1:1-Beziehung hatte keinen fachlichen Grund.

**Auswirkung auf Code:**
- `event_service.create_event()` setzt `status: "Accepted"` direkt beim `event_participation`-Insert
- Kein separater `participation`-Insert mehr
- `ticket`-FK zeigt jetzt auf `event_participation` statt `participation`

### 2. `event_media`: Eigener Primary Key

**Vorher:** `media_url TEXT` war der Primary Key.
**Nachher:** `media_id INTEGER GENERATED BY DEFAULT AS IDENTITY` ist der PK, `media_url` bleibt als normales NOT NULL-Feld.

**Warum:** URLs als PK sind instabil (CDN-Wechsel), haben schlechte Index-Performance, und verhinderten dass zwei Events das gleiche Bild teilen.

### 3. Alle Timestamps → `timestamptz`

**Vorher:** `timestamp without time zone` überall (außer `event_media.uploaded_at`).
**Nachher:** Alle Timestamp-Spalten nutzen `timestamp with time zone`.

**Warum:** PostgreSQL-Best-Practice. Ohne Zeitzone ist "15:00" mehrdeutig — Berlin? UTC? Die Konvertierung nutzt `AT TIME ZONE 'UTC'` für bestehende Daten.

**Betroffene Tabellen:** event, event_participation, location, person, ticket.

### 4. `event.date` → `event.starts_at` + `event.ends_at`

**Vorher:** `date timestamp` — ein einziges Zeitfeld, SQL-Keyword als Spaltenname.
**Nachher:** `starts_at timestamptz` + `ends_at timestamptz` (nullable).

**Warum:**
- `date` ist ein SQL-Keyword (erfordert Quoting)
- `starts_at` ist semantisch klar
- `ends_at` ermöglicht Dauer-Anzeige und "läuft gerade"-Logik

**Auswirkung auf Code:** Alle Backend-Schemas, Services, Router und Frontend-Types/Screens wurden von `date` auf `starts_at` umgestellt.

### 5. `max_capacity` und `scan_count`: NUMERIC → INTEGER

**Vorher:** `numeric` (für Dezimalzahlen wie Geldbeträge).
**Nachher:** `integer` mit CHECK-Constraint `max_capacity > 0`.

**Warum:** Teilnehmerzahlen und Scan-Zähler sind immer ganzzahlig. `integer` ist performanter und semantisch korrekt.

### 6. `location`-Felder nullable

**Vorher:** `street`, `house_number`, `postal_code`, `country` waren alle `NOT NULL`.
**Nachher:** Alle vier sind nullable, nur `city` bleibt `NOT NULL`.

**Warum:** Events wie "Sommerfest im Stadtpark" haben keine Hausnummer. Die API und das Frontend haben diese Felder bereits als optional behandelt — das hätte bei INSERT-Operationen zu DB-Fehlern geführt.

### 7. RLS-Policies und Grants

**Vorher:**
- RLS nur auf `event_media` und `person` aktiviert, aber **keine Policies** definiert
- `anon`-Rolle hatte volle Rechte (INSERT, DELETE, TRUNCATE) auf **allen** Tabellen

**Nachher:**
- RLS auf allen Tabellen aktiviert
- `anon`: nur SELECT (öffentliche Events + zugehörige Daten)
- `authenticated`: SELECT + INSERT + UPDATE (kein DELETE/TRUNCATE)
- `service_role`: voller Zugriff (Supabase-Standard)
- Basis-Policies: anon sieht nur `is_public = true` Events, authenticated sieht alles

```bash
# Option A: Supabase CLI
cd happin-backend

# Option B: Manuell im Supabase Dashboard → SQL Editor
# Inhalt von supabase/migrations/20260428165213_schema_optimization.sql einfügen und ausführen
```

## Bekannte Einschränkungen

- RLS-Policies sind noch sehr permissiv (authenticated kann alles lesen/schreiben). Feinere Policies (z.B. "nur eigene Events bearbeiten") kommen mit späteren Features.
- `event_media.media_url` hat keinen UNIQUE-Constraint mehr — gleiche URL kann mehrfach existieren. Wenn Deduplication gewünscht ist, muss ein Application-Level-Check hinzugefügt werden.
